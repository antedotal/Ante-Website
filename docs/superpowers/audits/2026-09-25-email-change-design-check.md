# Email-change design check — 25 September 2026

Read-only review of proposal, account readiness audit, website SSR/session helpers, and official Auth/SDK source. No provider requests, data reads, sends, or mutations. SDK installation was changing during review; exact 2.106.0 tag source was checked independently. This is source evidence, not hosted acceptance.

## Decisions needed before implementation

1. **Bind to a pending pair, not just either email.** Fresh `getUser()` must yield a nonempty `id`, valid current `email`, and valid distinct `new_email`. Snapshot `{id, currentEmail, pendingEmail}` before verification; accept the submitted email only if it belongs to that pair. Auth's actual User JSON maps `email_change` to `new_email`, so a separate pending table is unnecessary if the hosted authenticated `/user` response preserves this source behavior. Never substitute user metadata. A missing pending field fails closed. After verification, require the same user ID and either unchanged pair (pending) or confirmed email exactly equal to the snapshotted pending target with cleared pending state (completed). Checking only returned ID or “email advanced” is insufficient for replacement/concurrent requests. Postflight cannot undo a consumed OTP; do not claim atomicity across public Auth calls.

2. **Give `pending` a precise meaning.** SDK 2.106.0 `_sessionResponse` turns any successful JSON without user/session into null/null; it does not validate the `{msg,code}` first-confirmation envelope. `verifyOtp` also saves a returned session before the caller can check the user ID. Therefore the proposal's “unexpected null/null must not be accepted” is not implementable from SDK result shape alone. Recommended narrow choice: `pending` means only “the Auth account still has this uncompleted change”; never assert “this particular code was accepted” or mark one inbox confirmed using null/null alone. Return it only after error-null and a valid same-user, unchanged-pair postflight. If product requires per-inbox accepted state, add a tightly scoped fetch adapter that validates the actual known HTTP success envelope before SDK transformation; do not infer it from the nulls. No custom provider transport is needed for the narrower pending meaning.

3. **Use separate cookie stages.** The current `createCallbackClient` immediately mutates both request and provisional-response cookies. Do not use global `cookies().set` client here. Keep the initial verified identity/refresh stage isolated from the OTP stage, snapshot its cookies, and build the verify client over an isolated cookie jar. For pending, retain the initial authenticated session, including legitimately refreshed cookies if preflight refreshed it; do not clear or replace it with null. For completed, release OTP-stage cookies only after returned `data.user.id`, `data.session.user.id`, and authoritative postflight user all match the original caller and target. For wrong-account/malformed/error, discard every OTP-stage cookie. Merely returning a fresh response does not erase the helper's mutated request cookie jar; avoid reusing that jar for fallback identity checks. Test existing nonexpired cookies AND a preflight refresh, plus a wrong-account session written before SDK return.

4. **Completion and errors need an uncertainty path.** A successful provider verification followed by unavailable `/user` may already have changed the email. Return fixed 503, not invalid-code 401 and not completed. Retry may now have no pending state or a replayed code, so account state refresh is the recovery mechanism. Keep provider 429 distinct from invalid OTP and preserve fixed safe errors. Real hosted two-step acceptance remains gated on confirmations enabled, Secure Email Change enabled, template behavior, and authorized recipients; do not toggle shared hosted settings implicitly. Local test config must enable confirmations as well as double-confirm changes.

## Narrow confirmed-email synchronization decision

Use one private, fixed-search-path `SECURITY DEFINER` trigger function owned by the controlled migration/service owner with the privileges needed to update profiles. Auth's runtime role must not be assumed to have those profile privileges, and owner-only RLS cannot be satisfied by `auth.uid()` in a trigger. This is a justified internal definer function, not a browser RPC; revoke EXECUTE from PUBLIC/anon/authenticated. Fully qualify `public.profiles`. Trigger: `AFTER UPDATE OF email ON auth.users FOR EACH ROW WHEN (OLD.email IS DISTINCT FROM NEW.email)`; update only matching `profiles.id = NEW.id`, set only email to `NEW.email`, optionally add `profiles.email IS DISTINCT FROM NEW.email` to avoid redundant writes. Do not inspect pending fields, metadata or confirmation timestamps; Auth controls when confirmed `email` advances.

Preserve existing insert trigger, grants, policies and other columns. On missing profile, zero-row update is the narrow behavior: do not insert, and do not abort an otherwise valid Auth change to repair an unrelated preexisting integrity issue. Verify missing-row aggregates separately. The readiness preflight reports no mismatches or orphans, so no backfill is needed. SQL transaction tests should prove pending-field changes do nothing, actual email changes synchronize one matching row, nullable values are handled, unrelated rows/columns stay fixed, direct writes remain denied, and the internal function is not API-callable.

## Website staging and user admission contract

`createIsolatedAccountStage(request)` copies the incoming cookies into a private jar and returns a public-credential SSR `client` plus `fork()`. The baseline stage can refresh the verified caller; a fork starts with that jar but owns its own writes. `applyAccountCookieStages(response, baseline, acceptedChild)` is the only response write point. Apply the baseline alone on a fixed failure after identity succeeds; apply the child only after the route verifies the provider result and fresh account state. Cookie names merge in stage order, including SDK removal writes, with the shared Secure/Lax/root-path policy and private cache headers. Rejected child writes cannot mutate the original request or baseline jar. The isolated client replaces rejected network errors with a fixed error and replaces non-2xx Auth response bodies with fixed JSON before SDK logging, preserving numeric HTTP status for route classification. Successful responses pass through unchanged. Existing callback and proxy adapters remain unchanged.

After verified `getUser()` identity, `admitEmailChangeUser(id, 'request' | 'confirm')` consumes the deployed fixed five-per-minute callback RPC. It sends only an HMAC digest under distinct `website-email-change-request:v1:` and `website-email-change-confirm:v1:` namespaces. This bounds repeated provider email-change calls per account and action; the separate account visitor sixty-per-minute admission still runs before Auth in the route. Invalid identity/configuration or unavailable store fails closed with private 503 and Retry-After 60; a store denial returns private 429 with its validated one-to-sixty-second retry.
