# Ante website email-change backend contract (proposal)

25 September 2026. Read-only source and official Supabase documentation review. This file proposes the next slice; it is not a deployment or hosted acceptance claim. The account readiness audit is `Ante/docs/superpowers/audits/2026-09-25-website-account-contract-readiness.md` in the paired feature worktree.

## Current boundary

The website has a cookie-backed Supabase SSR client (`Ante-Website/lib/supabase/server.ts`), a Google PKCE code callback at `GET /auth/callback`, and separate public sign-in OTP endpoints at `POST /auth/email/request` and `POST /auth/email/verify`. The latter call `signInWithOtp(... shouldCreateUser: true)` and `verifyOtp(... type: 'email')`; they must not be reused for an authenticated email change. The account page currently shows the email claim and has no edit UI. Shared request code validates the configured site origin and bounds JSON to 4096 bytes. The website's local `supabase/config.toml` sets `double_confirm_changes = true`, but it does not establish the hosted setting. The account audit records that the live database has an Auth insert trigger and a profile-before-insert email copy, but no Auth email-update trigger. Its narrow profile grant release prevents direct authenticated writes to `profiles.email`.

## Proposed HTTP contract

1. `POST /api/account/email-change/request`, Node runtime and dynamic. Require canonical same-origin `Origin`, URL, Host, forwarded host/protocol; `application/json` under 4096 bytes; exactly `{ "newEmail": string }`. Trim and lowercase using the existing email parser, reject invalid and unchanged addresses. Require a valid current cookie-backed identity with `supabase.auth.getUser()` before provider mutation. Apply a durable per-user 5/minute request limit (and the existing visitor admission if useful); avoid logging addresses or provider details. Call only the public SSR client's `supabase.auth.updateUser({ email: normalizedNewEmail })`. Never call admin update or write `profiles.email`. Return `202 {"ok":true}` after provider acceptance, with private no-store headers and refreshed SSR cookies. This means **pending confirmation**, never changed. Fixed errors: 400 malformed/unchanged, 401 no valid identity, 403 untrusted origin, 413/415 body errors, 429 with `Retry-After`, 503 provider/limiter unavailable; map provider rejection to a fixed safe error without leaking whether the target email has an account.
2. `POST /api/account/email-change/confirm`, Node runtime and dynamic. Use the same origin, body, admission, no-store and safe-error rules; accept exactly `{ "email": string, "code": string }`, with the existing 6–10 ASCII digit string rule preserving leading zeroes. **Require an existing authenticated session before verification.** Obtain fresh `auth.getUser()` and snapshot a valid distinct current/pending address pair plus user ID; require the submitted address to belong to that pair before consuming any OTP. A user ID keyed durable 5/minute confirmation quota applies to signed-in calls. Sessionless calls consume the existing visitor-IP admission and return 401 before calling Auth, so an inbox link opened on another browser must first sign in to the same account. Call the public SSR client's `supabase.auth.verifyOtp({ email, token: code, type: 'email_change' })`. The SDK parses a first secure confirmation with **no user and no session**; an error-null result may return `200 {"status":"pending"}` only after authoritative postflight `getUser()` still shows the same user and unchanged address pair, preserving the preverified session and its refreshed cookies. Here `pending` means the Auth change remains incomplete; SDK null/null alone cannot prove which code was accepted. Only a result with an actual user and session may lead to `200 {"status":"completed"}` after returned identities and authoritative postflight user match the original caller and the confirmed email equals the snapshotted target with pending state cleared. Keep OTP-stage cookies isolated and discard them on mismatch/error, though a consumed token cannot be rolled back. Provider 429 remains distinct from invalid OTP; unavailable postflight returns fixed 503 because provider state may have changed. Reject invalid, expired, replayed, wrong-address and wrong-type codes with fixed safe errors and no provisional cookies. If per-inbox accepted state is required, validate the provider's HTTP success envelope at the transport boundary rather than inferring it from SDK null/null.

Use a dedicated email-change page to collect both codes and explain the pending state. Configure the **Change email address** Auth template to send an OTP (`{{ .Token }}`) appropriate to each inbox, avoiding link prefetch and fragment-to-SSR problems. Verify the exact rendering for the current and new inboxes in local mail testing before shipping. No `emailRedirectTo`, arbitrary `next`, or OAuth code exchange is needed for this OTP contract. The existing `GET /auth/callback` exchanges an OAuth PKCE `code`; an email-change code must instead use `verifyOtp` with `type: 'email_change'`. Supabase's server-side Auth guidance says PKCE email links require a token-hash verification endpoint, which is a separate possible link design, not part of this proposed OTP route. The website now pins `@supabase/supabase-js` and its Auth dependency to 2.106.0, keeping `@supabase/ssr` at 0.8.0. The real-SDK synthetic-transport test in `tests/supabase-email-change-compatibility.test.ts` failed on the former 2.93.3 lock because HTTP 200 `{msg,code}` was exposed as `data.user`; it passes on 2.106.0 with exactly null user/session and no error. It also checks completed-session, expired-code and provider-supplied `new_email` parsing. This proves local SDK compatibility, not hosted Auth configuration or delivery. Do not treat the old message object cast as an authenticated identity.

## Confirmed email sync

Add a narrow `AFTER UPDATE OF email ON auth.users` trigger with `WHEN (OLD.email IS DISTINCT FROM NEW.email)` that updates only `public.profiles.email` for `NEW.id`, using a fixed `search_path` and qualified names. It must read the confirmed `NEW.email`, never pending `email_change`/`new_email` fields and never user metadata. Revoke direct `EXECUTE` from `PUBLIC`, `anon`, and `authenticated` on the trigger function; preserve service ownership, existing profile grants/policies, and the current profile-before-insert email trigger. Treat missing profile rows as a separate data-integrity finding rather than inserting via website credentials. No bulk backfill or unrelated Auth synchronization is in this slice.

## Verification

- Unit/route tests: all malformed methods, origins, hosts, content types, oversized bodies, extra JSON keys, missing/expired sessions, unchanged/invalid/new duplicate email, rate limit, provider timeout and 429; ensure no Auth call before admission and no sensitive logs or response details.
- Provider-mocked contract tests: `updateUser` called once with only `{email}`; request returns pending 202; confirmation calls `verifyOtp` with `email_change`; first successful response `{user:null,session:null,error:null}` returns pending without clearing existing cookies; second successful response returns matching user/session and completed; old-only and new-only do not report completion when secure change is on; wrong/expired/replayed codes fail and return no cookies; sessionless and address-unbound calls never reach `verifyOtp`; a wrong-account user/session response is not installed. Keep the actual pinned SDK response test alongside provider-mocked route tests.
- Local database tests: profile email remains old while Auth has pending email; changes exactly once after confirmed `auth.users.email` update; no update for unrelated Auth metadata changes; ownership/grants still deny direct browser `profiles.email` writes; other profile columns and rows remain unchanged; trigger function is not directly callable by public API roles.
- Browser/local mail tests: current and new inbox get distinct usable codes with Secure Email Change enabled; either confirmation order works; cookies survive through the website proxy; sign-in with the new address works after completion, and the old address no longer acts as the account's primary email. Verify Google-linked accounts separately before claiming that identity path is supported.

## Configuration and acceptance gaps

Confirm hosted Secure Email Change remains enabled **and** hosted email confirmation/autoconfirm settings make the two-token path active; the current GoTrue source gates secure two-step verification on `!Autoconfirm` as well as `SecureEmailChangeEnabled`. The website's local config has `double_confirm_changes = true` but `enable_confirmations = false`, so a local run may not exercise two-step behavior. Confirm the hosted Change email template sends the intended OTPs to both addresses. Check hosted redirect/template settings if the implementation changes to links; this OTP proposal does not depend on redirect allow-list changes. The current email sign-in flow is backend preparation and provider delivery/cookies have not had real acceptance. Real two-inbox email-change delivery, hosted Auth behavior, SSR cookies through the Worker, and Google/email identity behavior remain blocked until Workspace and authorized test recipients are ready. Do not claim the feature live or complete from mocks or local SQL alone.

The user confirmed email editing and deferred real email tests. The compatible SDK is pinned and locally tested. Implementation still needs verified hosted two-step configuration, evidence that fresh `getUser()` exposes the pending `new_email` for preverification binding, and authorized two-inbox acceptance. If that pending field is absent, a separate server-owned pending-change record keyed by user ID is required before calling `verifyOtp`; do not fall back to accepting an unbound OTP. If product design later requires clickable links instead of codes, that is a separate UX choice and requires a dedicated token-hash confirmation route/template and prefetch protection.

[Supabase JS PR #2378](https://github.com/supabase/supabase-js/pull/2378) and its [2.106.0 changelog](https://github.com/supabase/supabase-js/blob/master/CHANGELOG.md) explicitly state that the SDK now maps this to `{user:null,session:null}`. These source facts do not establish the deployed GoTrue version or hosted configuration.
