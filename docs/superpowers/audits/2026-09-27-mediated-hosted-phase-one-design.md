# Mediated hosted phase one: bounded HTTP acceptance design

Status: proposed source contract under controller review; no implementation, credentials, provider requests or deployment. Supersedes the four open planning decisions in [contract gaps](2026-09-27-mediated-hosted-acceptance-contract-gaps.md), not the authoritative [mediated architecture](../../../../Ante/docs/superpowers/audits/2026-09-27-server-mediated-profile-read-design.md).

## Controller rulings and acceptance boundary

The next package is black-box HTTP acceptance only. Its success is `phase_one_http_passed`, never overall acceptance. Fresh per-request Auth/final-resolver traces, controlled hosted races, caller/target deletion transitions, real-browser behavior and runtime resource measurements remain required and unaccepted. Local tests establish runner safety, not hosted acceptance. Actual account, isolated Worker, intended HTTPS origin, source/deployment/config/cache-rule identities and approved SQL cutover receipts are mandatory operator pins. No preview URL, new account, paid workaround or automatic infrastructure creation is permitted.

The isolated acceptance Worker may use a unique run HMAC and exclusive fixture traffic; public Pages and production secrets stay unchanged. A separate build includes an operator-authenticated digest-preparation handler on that same origin/runtime. It performs no Auth, database or admission I/O. The normal build contains neither its route nor its credential/config references. Stronger single-invocation delay-only race probes are future design work; a validation-completion barrier must never be called proof of a mutation during synchronous WASM.

Only the separately named `hosted-profile-photo-mediated*` family is added. Historical runners and failed receipts are preserved. Production reader authorization, cache policy, deadlines, quotas and credentials are unchanged. The runner cannot execute release install/rollback, change cache rules, rotate secrets, deploy artifacts, enable modes or start/stop admission cleanup jobs.

## Preparation artifact: minimal contract

Add `scripts/acceptance/mediated-preparation-worker.mjs`, exporting `prepareDigests(request, env): Promise<Response>`, and `worker-mediated-acceptance-entry.mjs`, wrapping the existing `worker-entry.mjs`. The wrapper handles only exact `POST /__ante_acceptance/profile-read-digests-v1`; all other requests delegate unchanged. A separate `wrangler.mediated-acceptance.jsonc` uses that entry, the same runtime flags/assets/self-binding shape as the ordinary config, `workers_dev:false`, `preview_urls:false`, and no routes/domains/secrets or enabled mode checked in. It is a build artifact, not deployment permission. Build verification must prove the ordinary bundle excludes this module and all `ANTE_ACCEPTANCE_*` environment names.

Operator-supplied runtime values: `ANTE_ACCEPTANCE_RUN_ID` (canonical UUID), `ANTE_ACCEPTANCE_ORIGIN` (exact pinned HTTPS origin), `ANTE_ACCEPTANCE_OPERATOR_TOKEN` (64 lowercase hex, independently random), `ANTE_AUTH_LIMIT_HMAC_SECRET` (unique to this run, at least 32 UTF-8 bytes), and `ANTE_AUTH_INGRESS=cloudflare`. Never persist any secret/token in the journal. Requests require exact `Authorization: Bearer <operator token>` and JSON `{run_id, fixture_ids:[A,B,C]}`, three distinct canonical UUIDs in journal order. Allow no extra fields, query, body over 1024 bytes, redirects, cross-origin URL or `cf-worker` header. Compare fixed-length operator-token bytes with `timingSafeEqual` after strict format validation. Consume the request body with a 2-second/1024-byte bound. Invalid input/config/auth/ingress uniformly returns fixed 404 JSON; success is exact `{version:1,run_id,visitor_digest,user_digests:[digestA,digestB,digestC]}`. All responses use the production photo no-store header contract, no CORS, no validators, no Set-Cookie and no diagnostic logs. No network fetch or durable/runtime-global state is allowed.

Derive visitor digest using precisely the canonical-IP algorithm/domain in `callback-admission.ts`, including mapped IPv6 and sentinel rejection, from genuine Cloudflare `cf-connecting-ip`. Derive user digests only with `website-photo-read:v1:` plus each UUID. Visitor domain is `website-account:v1:`. Do not accept arbitrary domains/messages, return IP/secret or authorize any photo with these values. Implement the small pure derivation locally in the preparation module; parity tests against the production admission fetch body pin its behavior without changing production source.

Fixture creation intents and reconciled IDs precede preparation. The runner journals its single preparation intent and reserves one preparation request. The exact body and its digest are deterministically reconstructed from the already-durable immutable run UUID and ordered reconciled A/B/C IDs; no duplicate mutable body-hash field is stored. A reload test must prove this reconstruction equals the actual serialized HTTP body, and unbound or mismatched IDs must reject before network. It then persists all four returned distinct digests before any website-photo dispatch. Preparation failure after creating users still invokes reserved identity cleanup. Runtime HMAC is never loaded by the runner. Immediately verify all four digests have zero rows; the entire admission table must have been empty at preflight. A fixed direct Node HTTPS connection pool sends preparation and website requests; no proxy, browser or client-supplied ingress header is used. Unexpected ingress/IP changes cannot be ruled out locally: admission inventory after every photo request detects any unjournaled digest and blocks the run/unknown-row cleanup. Do not describe connection reuse as proof of stable ingress.

The successful 2/3-call observations are not dispatch ceilings. Every photo request reserves the same 26-call Auth envelope defined below, including ordinary requests whose genuine session enters the SDK refresh margin. No TTL/clock-skew prerequisite or production behavior change is added. Hosted receipt calls this induced SSR-refresh compatibility and actual sampled Auth-body compatibility, not exhaustive acceptance of every possible 64 KiB user document.

## Exact dispatch budgets and deadlines

All counters reserve durably before dispatch, including read-only/preparation requests. For a website request reserve its entire internal envelope before dispatch because the external journal cannot intercept Worker calls. These are conservative reservations, not observed traces; do not reclaim on denial/error. Separate direct/subrequest counters prevent double counting. The external runner never automatically retries, follows redirects or reconnects-and-resends. This prohibition does not disable the unchanged installed SDK's internal refresh retries, which are included in its separate Worker Auth reservation. Each HTTP response/body is capped at 10 seconds (website 35 seconds to encompass its unchanged 30-second route cap), provider JSON/errors 16 KiB, direct Auth success 64 KiB, preparation JSON 1 KiB and fixture image bodies 4 KiB. Reject unexpected compression/partial bodies; count bytes while reading and cancel late replies. Run phase stops dispatching at 900 seconds from journal creation; cleanup has a separate 300-second epoch. Late/uncertain effects are not made safe by a local deadline. Initial cleanup binds `cleanupStartedAt` durably once before its first HTTP or CLI dispatch; the timestamp must follow run creation and cannot be rewritten. Every cleanup transport reads that persisted 300-second epoch and fails closed if it is absent; no process-local restart extends it. Explicit recovery uses its existing immutable epoch start.

Reserve this loose envelope uniformly even for anonymous/early-denied cases, without relying on favorable refresh deduplication, cookie expiry or scheduling. It is source-derived reserved capacity, not an observed hosted count or tight maximum. Task 3 must prove at most 26 dispatches with the actual pinned SDKs for immediate repeated 503s, network failures, retry-then-success, each initialization/listener/explicit session load, sessions entering the refresh margin and short-lived refreshed sessions, under the shared deadline. ## Cleanup, ambiguity and receipts

Admission cleanup is scoped to four immutable digests, zero baseline, exclusive run traffic and bounded journaled interval. Reconcile exact row IDs from inventories; reject an unexpected digest, timestamp, excessive count or previously observed row whose immutable fields changed. Scheduled expiry may remove owned rows. Under the same digest advisory locks used by admission, delete only proven remaining rows; do not recreate expired rows, disable cron or delete unknown rows. Full final 22-table fingerprint must equal baseline. Ordinary sequence advancement is not included in existing table-row digests; report this preserved historical definition, never reset sequences.

Reuse historical ownership checks but implement the new two-generation states: G1 revision 1; G2 revision 2; clear revision 3. Cleanup reconciles missing acknowledgments from authoritative operations/head and never reissues creation/reserve/bind/prepare/upload/publish/clear. An uncertain upload with missing object is blocked. Inspect all protected references/multipart/foreign buckets/owner prefixes before metadata teardown; exact marker/email/created-at/profile/manifest/revision mismatch blocks that branch. Delete owned friendship/profiles/head/operations transactionally in established publication lock order; verify only owned objects remain; exact Storage deletes; complete user-reference checks; exact Auth deletes; admission cleanup and 22-table/catalog comparison. Partial identity creation must use the same safe generalized teardown without assuming three users exist.

A website timeout, lost response or unexpected 503 can leave an admission RPC unsettled; cancellation is not proof of rollback. Mark uncertain website dispatches permanently. Attempt only independently proven safe cleanup branches, retaining the journal and `cleanup_blocked` for possible late admission effects. For those uncertain dispatches, admission deletion/final completion require a separately supplied operator settlement receipt establishing the isolated Worker accepts no more test traffic and relevant in-flight database work has settled; never infer this from a sleep or a request timeout. Its exact fields are `{run_id,origin,deployment_id,closed_to_test_traffic:true,website_calls_settled:true,admission_writes_settled:true,issued_at}`; supplied file SHA256 and timestamp are recorded in the recovery journal and must bind the same run/origin/deployment and follow the uncertainty. It is explicitly an operator attestation, not runner-observed provider proof. Unknown-digest rows cannot be deleted even with that receipt. Recovery can reconcile exact settled owned rows; cannot turn failed phase-one assertions into a pass.

Journal version 3 and receipt version 2 retain append-only `directObservations` with fixed descriptors, numeric status and checked `denied|empty_list` results (plus `capability_unverified` for render rows), excluding IDs, URLs and raw bodies. Exactly 308 unique matrix rows and 16 unique Data rows, bound to reserved descriptors and observed counters, are required before phase-one success; reconstruction rejects missing accepted-run rows, duplicates or history rewrites. Receipt separates `phase_one_http_passed|failed`, cleanup state, preservation state, supplied operational attestations, observed HTTP assertions and reserved versus observed dispatch counts. Permanently list phase trace/race/browser/resource/profile-deletion gates as `not_accepted`. A receipt with failed cleanup, missing catalog/fingerprint agreement, missing matrix rows or uncertain provider response is not phase-one accepted. Retain private journals outside Git; committed receipts include only fixed case labels, statuses, bytes/digest checks, safe pins and counts, not fixture identities or provider secrets.
