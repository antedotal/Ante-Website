## Selected contract and established backend

- Private `profile-photos` bucket; exact `<verified lowercase owner UUID>/avatar` key. PUT/DELETE at `/api/account/profile/photo` use fresh public-key Auth verification for owner identity, durable visitor plus per-user action admission, and service-only Storage upsert/remove. GET `/api/profiles/[ownerId]/photo` downloads through the caller JWT so the Storage policy decides owner/current accepted-friend access. No signed/public URLs, redirect, legacy `avatar_url` fallback, or image optimizer. Missing/denied reads are indistinguishable 404. All responses private/no-store, photo response has validated MIME and `X-Content-Type-Options: nosniff`; verified refresh cookies survive downstream failures. Uncertain writes return 503 and are not replayed automatically.
- The paired SQL release in `Ante/supabase/releases/private-profile-photos/` created an empty private bucket limited to 2 MiB JPEG/PNG. Its single authenticated SELECT policy requires the `object.get_authenticated` operation, exact lowercase UUID key, target and caller profiles, and owner or current accepted friendship in either orientation. No direct user write policy exists. Local real Storage HTTP acceptance passed; hosted Storage/CDN/JWKS/cache, direct transform nonexposure, and website acceptance remain open. The website must stay inactive until those gates pass. This is a documented receipt, not a new provider check here.

## Reusable website seams

- `lib/server/account-request.ts`: `trustedAccountOrigin(request, siteOrigin, requireOrigin)` validates canonical URL, Host, optional Origin and forwarded host/protocol; use `requireOrigin=true` for PUT/DELETE. Existing `boundedAccountJson` is 4096-byte JSON only and cannot validate binary uploads. A distinct bounded stream reader is needed; the concurrent validator task owns that area. Check the route, query, origin, cheap headers and feature gate before admission; read or decode the upload body only after visitor admission, fresh verified identity and per-user upload quota.
- `lib/server/callback-admission.ts`: `admitAccountVisitor` is the first network operation for valid account routes, checks direct Cloudflare identity, and consumes the fixed 60/min visitor RPC. `admitEmailChangeUser` shows a verified-ID HMAC namespace and fixed per-user action admission using `consumeCallbackLimit`, 5/min. The store (`lib/server/callback-limit-store.ts`) accepts only two fixed RPC names, strict response shapes, a 5 s timeout, no redirects/cache, and private service credentials. Photo operations need distinct per-user namespaces so upload, delete and read do not collide with email buckets. **Default:** use callback 5/min separately for upload and delete, account 60/min for read, keyed by HMAC of verified caller ID plus `website-photo-{action}:v1:`; share the existing RPCs and HMAC secret, not a new table. If a different quota is required, that needs a SQL contract change. PUT order: canonical request, cheap header checks and feature gate; visitor admission; fresh Auth; per-user upload quota; bounded body read and decode; then Storage. Read quota is called for by the selected contract even though the present visitor RPC alone is IP keyed.
- `lib/supabase/config.ts` validates the configured public project URL/key and canonical site origin. `lib/supabase/server.ts:createCallbackClient` provides a request-scoped public-key SSR client and provisional response cookie jar. `lib/server/account-session.ts:verifyAccountUser` calls `auth.getUser()` but returns status only. Photo endpoints require the actual freshly verified UUID. **Default:** add a narrow shared helper that returns `{id}` or the existing fixed 401/429/503 class from one `getUser()` call; avoid a second call or `getSession().user` as authority. Require the canonical lowercase UUID spelling before interpolating a fixed key. `withVerifiedCookies` copies only cookies staged after successful verification; all later 404/429/503 and successful GET bytes need it. A failed Auth check returns a fresh response without provisional cookies.
- `lib/supabase/isolated-account-stage.ts` is the stronger baseline/child cookie pattern for Auth mutations. Photo mutations do not call Auth mutation methods, so a single provisional verified SSR stage is probably sufficient. If a separate stage is introduced for Storage, only release it after verifying its intended result. `createAuthFetch` sanitizes only `/auth/v1` transport/errors; Storage errors and transport are currently raw and must be mapped to fixed route responses without logging bodies, paths, IDs or credentials.
- `lib/server/callback-limit-store.ts:serviceCredential` is private and presently confined to admission. The selected photo contract explicitly allows expanding a server-only credential to fixed-key Storage writes/deletes. **Default:** move its parsing/validation into a `server-only` shared credential helper, with its existing behavior unchanged, and build a tiny Storage adapter accepting only a validated owner ID and `put`/`delete`. No caller URL, path, bucket, arbitrary method, Authorization header, or cookie crosses this adapter. Do not import `lib/supabase.ts`: that is a waitlist client with placeholder fallback. A `sb_secret_` key currently uses `apikey` only in the REST admission adapter; legacy service JWT also uses bearer. Confirm actual Storage gateway credential behavior in isolated/hosted acceptance before enabling; do not assume the REST RPC header pattern proves Storage upload works.
- `app/api/account/profile/route.ts` and `app/api/account/ante-presets/route.ts` show `dynamic='force-dynamic'`, `runtime='nodejs'`, fixed method handlers and explicit bodyless 405 for HEAD/OPTIONS/other methods before Auth. The new mutation route needs `Allow: PUT, DELETE`; the GET route should use `Allow: GET`. Keep API admission in the route; `proxy.ts` matches account pages, not API routes. Their JSON `answer` helpers are private/no-store; photo GET needs a byte response, explicit `Content-Type`, `nosniff`, no-store and verified cookies. Never forward unvalidated Storage headers or error bodies.

## Minimum route behavior and failure decisions

- PUT: enforce canonical same-origin write request, no query, cheap content-type/content-length checks and a closed feature gate first. Then perform visitor admission, fresh owner verification and per-user upload quota before any streaming body read or image decode. Apply the bounded stream reader and validator, then service-only fixed-key upsert with conservative upload cache control; return success only after confirmed provider success. Reject malformed/too large/unsupported images with fixed 400/413/415 as applicable. Provider/transport ambiguity is 503; no automatic retry because the object may already have changed. The selected 2 MiB/JPEG/PNG limit matches the deployed bucket. The validator implementer owns decoder modules/config, so this note does not prescribe its implementation.
- DELETE: same origin, no query, reject or tightly define request body; visitor admission, verified owner, separate delete quota; service-only fixed-key remove. Return idempotent success for a missing object only if the provider response reliably confirms that state. Treat uncertain or malformed provider results as 503. A write may race another write/delete; the contract does not promise click ordering.
- GET: canonical request and lowercase target UUID, no query, visitor admission, fresh caller Auth, separate per-user read quota, caller-JWT authenticated Storage `download` for the exact target key. Read with the request-scoped public-key client so Storage RLS rechecks friendship at request time; do not use the service credential for photo reads. Map missing/unauthorized to the same private 404; map unknown/transport failures to fixed 503. Bound downloaded bytes and verify returned bytes/MIME before sending; attach refresh cookies to 404/429/503 and success after verified identity. If Storage headers or cache indicate bypass, leave serving disabled. Already delivered bytes cannot be recalled.
- **Default activation:** a server-only photo mode gate (unset by default, no `NEXT_PUBLIC_` variable), checked before admission/Auth/Storage, returning private 503 while closed. Open it only after validator Worker compatibility/resource checks, fixed-key credential behavior, hosted user-JWT read/deny and cache revocation, direct transform nonexposure, browser/Worker cookie acceptance and no leaked service credential. Merely having the bucket/SQL or passing local origin tests does not open the route.

## Controller follow-up

The validator is still under implementation/review. Do not dispatch endpoints until its usable interface and release limitations are accepted. Expensive upload stream reading and decode must follow visitor admission, fresh verified identity and per-user quota. A fixed-key write using the privileged credential does not itself establish an existing application profile; the endpoint implementation must verify that prerequisite and document the remaining concurrent account-deletion cleanup dependency. Final implementation must specify how the exact caller token used for authenticated Storage reads is correlated with fresh Auth verification without trusting cookie user metadata. Proposed defaults above are not completed code.

Source checks on 26 September used installed supabase-js/storage-js2.106.0: upload uses POST with x-upsert, returns Id/Key, and remove uses DELETE of the bucket with a prefixes array. The completed local HTTP fixture used single-object DELETE, so it does not yet establish the SDK bulk-remove reply shape or missing-object semantics. Cover the actual selected adapter protocol rather than treating those APIs as interchangeable. Official [private-download guidance](https://supabase.com/docs/guides/storage/serving/downloads) confirms the authenticated object endpoint with caller Authorization. Current changelog review found no new relevant Storage route migration; exact hosted acceptance remains required.
