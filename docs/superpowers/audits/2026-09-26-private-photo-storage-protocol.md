The single-object route is **officially exposed**, not an undocumented private route: the [Storage service's published OpenAPI JSON](https://supabase.github.io/storage/api.json) contains `DELETE /object/{bucketName}/{*}` (“Delete an object”) and its HTTP 200 `{message:string}` schema. It also contains `DELETE /object/{bucketName}` (“Delete multiple objects”). The pinned source registers both routes; the existing Ante local HTTP harness used the single path and proved service-role replacement and deletion, but only asserted deletion status, not its JSON body or the missing-object case: [`private-profile-photos-http.test.mjs`](/Users/daniel/.codex/worktrees/ante-web-first-foundation/Ante/scripts/backend/integration/private-profile-photos-http.test.mjs).

Installed `@supabase/storage-js@2.106.0` uses the **bulk** route for `.remove([path])`: `DELETE /object/<bucket>` with JSON `{ "prefixes": [path] }`; see [`StorageFileApi.ts`](/Users/daniel/.codex/worktrees/ante-web-first-foundation/Ante-Website/node_modules/.pnpm/@supabase+storage-js@2.106.0/node_modules/@supabase/storage-js/src/packages/StorageFileApi.ts). Pinned bulk implementation returns HTTP 200 with an array of deleted database objects, and can return `[]` when nothing was deleted, including when a scoped deletion sees no rows; see [`deleteObjects.ts`](https://github.com/supabase/storage/blob/01c95148a981a88b5f7e9014571a2926567b51e3/src/http/routes/object/deleteObjects.ts) and [`object.ts` deleteObjects](https://github.com/supabase/storage/blob/01c95148a981a88b5f7e9014571a2926567b51e3/src/storage/object.ts). Current [JavaScript remove docs](https://supabase.com/docs/reference/javascript/file-buckets-remove) describe the bulk client API; the [Storage delete guide](https://supabase.com/docs/guides/storage/management/delete-objects) recommends removing through the Storage API rather than SQL.

## Recommended fixed-key adapter contract

Use the already locally exercised single-object paths. For upload, require a 2xx HTTP status, parse a small JSON object, and require `Key === 'profile-photos/' + uuid + '/avatar'`; if present, `Id` must be a nonempty string. Do not hardcode HTTP 200 for upload because the pinned handler delegates the success status to backend metadata. For delete, accept only HTTP 200 with `message === 'Successfully deleted'`, or the precise pinned missing-object case (HTTP 400 and JSON `statusCode === '404'`, `code === 'NoSuchKey'`, `error === 'not_found'`, `message === 'Object not found'`) as an idempotent no-op. Treat any other success/error body as an upstream protocol failure. A fixed path built solely from an authenticated server-validated UUID prevents caller-selected object keys. The adapter should set bounded timeout, `redirect: 'error'`, `cache: 'no-store'`, and keep credentials and upstream error bodies out of logs/client responses. The website should authorize the operation before using a privileged key.

This reply matching is a recommendation based on pinned source. It needs a focused hosted synthetic-account check before claiming hosted success, especially the missing-object wire response and actual upload status/JSON.

## Credential boundary

Current [Supabase API-key docs](https://supabase.com/docs/guides/getting-started/api-keys) and [migration guide](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) say an opaque `sb_secret_...` belongs only in the server's `apikey` header, not `Authorization: Bearer`; it maps to `service_role` and bypasses RLS. A legacy service-role JWT can be sent as `apikey` plus `Authorization: Bearer <JWT>`. This matches the website's existing server-only [`callback-limit-store.ts`](/Users/daniel/.codex/worktrees/ante-web-first-foundation/Ante-Website/lib/server/callback-limit-store.ts) credential split. The pinned self-hosted Storage origin itself registers JWT auth for these object routes ([`index.ts`](https://github.com/supabase/storage/blob/01c95148a981a88b5f7e9014571a2926567b51e3/src/http/routes/object/index.ts)); its local synthetic JWT test does **not** prove the hosted Supabase gateway accepts `apikey`-only opaque secret keys for Storage. Keep that exact gateway behavior as an explicit hosted verification gap; never substitute an opaque key into a Bearer header to work around it.

The Supabase skill's changelog check found no Storage-specific breaking notice that changes this pinned contract. Current docs remain useful for gateway/key guidance, while the pinned Storage source governs the adapter response logic.
