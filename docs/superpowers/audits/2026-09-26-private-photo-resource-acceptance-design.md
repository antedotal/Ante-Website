## Recommendation

Build a boundary-corpus and profiler mode around the existing temporary actual-OpenNext-Worker runner. Treat its result as local resource characterization, not activation acceptance. Prioritize maximum legal images, worst supported PNG bit depth, almost-2-MiB bodies, and proven overlapping preflight operations. Do not spend another cycle on tiny-image status tests. Do not block this local work on the unanswered Workers plan, but do block numerical hosted CPU acceptance on that answer.

The present `decoderBusy` guard starts only in `fullyDecodeProfilePhoto`. `readProfilePhotoBody` and all of `inspectPng`, including stream decompression, precede it. Therefore one simultaneous codec call does not imply one simultaneous resource-heavy validation. A bounded benchmark can expose this and quantify selected loads; it cannot establish a universal concurrency bound. If evidence confirms material pressure, the smallest follow-up is a whole-validator no-queue admission guard acquired before body buffering and released in `finally`, with cancellation of denied bodies. That changes runtime admission semantics and deserves its own focused implementation/review, not an invisible harness patch. Uploaded and downloaded byte ownership outside the validator must also be included before claiming endpoint-wide bounds.

## What tools really establish

Cloudflare documents local CPU profiling through Wrangler DevTools and memory heap snapshots. CPU profiles identify expensive JS/WASM paths on this machine. Heap snapshots identify retained objects and allocation families. Neither is a reliable exact hosted per-request CPU meter or total transient per-isolate memory high-water meter. Worker `performance.now()` readings must remain labelled wall observations; platform timers advance on I/O, and network elapsed time is not CPU. Current open-source workerd server implementation explicitly has a LimitEnforcer section stating no limits are enforced. A passing local run, or setting `limits.cpu_ms`, is not evidence of hosted limit enforcement.

Cloudflare currently documents 128 MB per isolate, including JS and WASM, shared by concurrent requests. Free HTTP CPU limit is 10 ms; Paid default is 30 seconds with configurable maximum 5 minutes. Target account plan and configured limit remain unknown. Hosted invocation logs expose CPU and wall time; the docs show exceeded-memory outcomes, not an exact ordinary per-invocation peak-memory counter. Do not promise that deployment alone will produce a peak-memory number.

## Concrete harness scope

1. Keep the existing synthetic-only, temporary-route OpenNext build and final clean rebuild. Add an optional resource mode rather than replacing the quick correctness run. Use a fresh preview process for each cold case; use one persistent preview for warm/concurrent/retention cases. Record commit, lockfile hash, OS/CPU, Node, Wrangler, workerd, OpenNext versions, flags, fixture SHA-256, bytes, dimensions, PNG depth/color or JPEG component/scan facts, status/error code and run identifier. Do not record image bytes in logs.
2. Bind HTTP and inspector to loopback, use a temporary HOME, allowlisted env and dotenv refusal, and explicitly disable telemetry. Refuse busy ports before startup; readiness must include a random per-run route nonce, not any HTTP answer from a pre-existing listener. Refuse remote bindings/provider operations. Kill/wait for the complete owned preview process tree and verify listener shutdown; preserve cleanup on signals/failure and verify diagnostic route absent from source and final artifacts. These are necessary harness boundaries, not new production configuration.
3. Offer an inspector hold/profile mode using the exact installed Wrangler's inspector support. First capability-probe its local inspector endpoint; identify the actual app isolate rather than a proxy/router isolate. Use standard CDP `Profiler.enable/start/stop` if supported to save `.cpuprofile`, otherwise document a reproducible DevTools export. Report sampled active CPU estimates/hotspots, interval, idle/GC attribution and machine dependence; do not divide total profile wall duration by request count and call that CPU.
4. Save baseline and post-batch heap snapshots in a separate diagnostic run. Optional inspector allocation sampling or heap-usage counters require capability detection and explicit coverage labels; unsupported measurements must say unavailable. Snapshots/GC change execution and can miss freed transient data. Do not treat heapUsed as total JS+WASM+native peak. A local OS workerd-process RSS sample may be recorded only as process-level corroboration (includes runtime/other isolates and can miss peaks), never renamed isolate memory. Do not count all virtual address reservations as committed WASM bytes.
5. For a bounded second diagnostic pass, use temporary source-map breakpoints at body assembly, PNG inflation progress, codec entry and post-decode while pixels are live. Inspect retained ArrayBuffer and WASM-memory backing-store accounting and whether the tooling actually includes it. Do not instrument shipped codecs or add permanent production diagnostics. CPU measurements must use the unpaused pass. If accounting cannot cover a category, retain that gap explicitly instead of constructing a false precise sum.
6. Output JSONL case outcomes plus a small Markdown receipt linking raw profiles/snapshots, describing coverage and explicitly leaving hosted gates open. Check the fixture generator and report aggregation with focused tests; run the resource harness once plus targeted reruns only for failures/new changes.

## Bounded fixture matrix

Generate deterministic synthetic assets outside the Worker; reuse installed codecs/tools where available, adding no service, Docker dependency or purchase. PNG can be generated directly with Node zlib and correct CRCs. Use a documented offline JPEG generator with recorded settings; exact generation dependencies must be pinned if added. Verify fixtures before benchmarking so a malformed generator output cannot masquerade as resource rejection.

- Real maximum area: 2000×2000, not 2048×2. Also 2048×1953 (3,999,744 pixels), rotated counterpart, and very thin axes. Exercise PNG RGBA8 and RGBA16: RGBA16 at 2000×2000 has 32,002,000 expected preflight scanline bytes before the codec's separate decode and final 16,000,000 RGBA bytes. This is materially different from the existing tiny fixture.
- Flat/highly compressible and deterministic patterned images; ensure actual compressed payload stays at or below 2,097,152 bytes. Add valid permitted metadata to reach exact byte cap when necessary; name it metadata-padded rather than claiming high-entropy image stress. Separate near-cap compressed IDAT/entropy payload cases from metadata padding, since CPU paths differ.
- Baseline and progressive JPEG at maximum area, including accepted grayscale and multi-component cases generated by a trustworthy offline tool; record scan count. A maximum-area RGB JPEG does not cover all accepted SOF/component combinations.
- CRC-valid PNG whose inflated length reaches expected then exceeds it; valid-length PNG with an invalid late scanline filter; bad CRC near the end; up to the accepted 4096 total chunk boundary and one above, using bounded IDAT splits. JPEG late entropy corruption/warning with framing and EOI retained. Ensure expected 422 and a following valid image succeeds.
- Exact byte cap and cap+1, declared and unknown length; stream partitions 16 KiB and deliberately small 1 KiB. Slow/aborted bodies as a bounded separate case, not interleaved with CPU timing. Reject wrong expectations rather than accepting any 4xx.

Run three fresh-isolate cold attempts for the largest valid PNG/JPEG; then 20 sequential warm requests per representative class. Run simultaneous bursts of 2, 4 and 8 maximum-area PNG requests, mixed PNG/JPEG, and maximum-byte streamed bodies. Follow each burst with a valid image and an ordinary cheap app route. Finish with 20 alternating valid/late-malformed waves at concurrency 4 (80 requests). These are bounded screening sizes, not production workload guarantees. Avoid p99 claims from small samples; report every cold value and warm median/max.

The temporary route should return a per-isolate nonce and track active validator calls/max overlap without retaining request data. For streamed bursts, start each request with enough bytes to enter its body read, hold briefly, then release the remaining bytes together. Assert overlap and one isolate identity; four coincident client promises yielding four 200s are not proof of contention. Optional staged diagnostic breakpoints can establish overlapping PNG preflight. A busy 503 is acceptable only for the actual busy path, and must not substitute for valid sequential acceptance. For a whole-pipeline guard follow-up, require evidence that losers never read/copy/inflate, all outcomes release capacity, and the next valid request succeeds.

## Costs and decision criteria

Local harness costs are developer time, one probe build and one clean rebuild, local CPU/RAM, fixture storage and potentially large heap snapshots. No hosted usage or paid-resource cost is needed. Cap snapshot count (baseline, post-largest, post-sustained) and apply a whole-run timeout; preserve artifacts on failure. The corpus/profile support is a bounded script/fixture-helper/report change, not a production endpoint or codec replacement.

Local acceptance means: maximum supported cases decode; typed denials/recovery hold; overlap is actually exercised; no unbounded retained-growth trend is visible in the sampled workload; major CPU/allocation contributors and measurement gaps are recorded. A concerning RSS/heap/profile result blocks progress; a good result only narrows uncertainty. Do not create a pass threshold such as “snapshot <128 MB” or “local wall <10 ms.”

Release still requires the actual Workers plan/configuration, an approved CPU headroom target for complete GET/POST routes, hosted invocation CPU/outcome evidence for representative cold/warm/malformed/concurrent traffic, and an explicit memory case covering baseline app allocations, both warmed codec heaps, transient native inflation/decode allocations, buffered provider/request bodies and controlled overlap. Local source-level allocation/concurrency bounds plus calibrated profiling may support memory acceptance; ordinary hosted success/error rates alone cannot prove exact peak. If no dependable total-memory measurement or defensible bound is available, retain the gate and narrow the accepted input/codec/concurrency design instead of declaring success.
