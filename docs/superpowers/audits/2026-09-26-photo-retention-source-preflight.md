## Existing seams and conflicts

- Mobile `app/verification/camera.tsx:159,229` uses quality 0.8 with no explicit 1080 dimension bound. `:260–319` uploads `<taskId>/<timestamp>.jpg` then submits that path. Upload success plus failed submission can orphan a file. Compression belongs before upload, and submitted identity must refer to final stored bytes. Both SDK and native fallback must send the same transformed content and matching MIME.
- Backend `supabase/migrations/20260916000002_unify_verification_and_private_storage.sql:44` serializes submit against the task and binds verifier rows to attempt number. It stores one latest proof path, not an immutable attempt asset ledger. Review resolution clears that path on success, first rejection and final rejection (`:296–349`). Storage helpers protect current submitted evidence but permit owner deletion when failed/completed/archived or proof timestamp null (`:539+`). Those rules cannot themselves express retention or dispute holds.
- There is a competing source lineage: `supabase/forward/20260917111148_task_authority_v1.sql:597+` rejects proof lifecycle for authority-version tasks (`LIFECYCLE_NOT_READY`), keeps different legacy submit/review bodies and has direct SQL storage metadata deletion at `:796`. Its `delete_old_deleted_tasks` only purges legacy tasks after seven days (`:912`). Do not apply a migration-only change without verifying which deployed definitions and task cohort are authoritative.
- Mobile `contexts/TasksContext.tsx:224–239` reacts to one verifier approving by calling cleanup. `:293–324` nulls proof metadata and deletes the entire task folder, also invoked by deletion/completion paths (`:999,1089,1183`). A single approval may precede majority and must not initiate retention deletion. These callers would defeat a new retention policy even if a scheduler were correct.
- `supabase/functions/purge-deleted-tasks/handler.ts:133+` purges seven-day archived tasks, excludes only payment holds with status `requires_capture`, then removes every folder image and deletes task rows. Storage listing/removal errors are swallowed before task deletion. This does not cover captured/settled but disputed financial evidence, review/resubmission, retryable cleanup state, or atomic revalidation.
- Website `docs/contracts/profile-photos.md` and `lib/server/profile-photo-store.ts` implement a fixed `<ownerUuid>/avatar` object with privileged upsert/delete; GET uses caller JWT. `lib/server/profile-photo.ts` fully validates/decodes then returns original bytes. Endpoints are gated closed. Contract explicitly leaves concurrent account deletion cleanup unresolved. A delayed cleanup of this fixed key can delete a newly uploaded avatar. Active avatars must not expire simply because their creation is old; upsert already replaces prior bytes at this key.

## Recommended implementation boundaries

1. Add an authoritative immutable asset/attempt record before clearing existing proof projections: asset ID, task/owner, attempt, exact bucket/key, final format/dimensions/bytes/hash or equivalent identity, submitted/terminal timestamps, superseded status, retention due date, hold reasons and cleanup status. For nonfinancial proof, the seven-day retention clock starts only at authoritative final resolution, never supersession or upload age. Preserve unresolved older attempts across resubmission. Replaced-avatar cleanup is a separate lifecycle and must not expire the active avatar.
2. Server eligibility must fail closed for active tasks, pending review, open resubmission, disputes and financial/evidentiary holds. Unknown legacy classification is not proof of eligibility. A terminal boolean or absence of `requires_capture` alone is insufficient. Financial policy remains a separate explicit decision; no blanket 30/90-day financial evidence deletion.
3. Replace all opportunistic mobile/folder deletions with server-authoritative intent; preserve reference/ledger metadata until Storage deletion is acknowledged. Use bounded authenticated scheduled batches and durable retry state, revalidate/claim eligibility under the same lifecycle authority, delete exact immutable keys through Storage API, then record a tombstone. Never delete Storage metadata through SQL. Protect against revival/new holds during deletion with a lifecycle protocol, not only a preflight SELECT.
4. For new proofs, normalize/resize before committing submission and bind reviewers to that immutable normalized artifact. Replacing bytes in place after review changes what an existing attempt means; changing the key without atomic reference/authorization updates breaks pending reviewers and signed URLs. Bind the accepted proof identity to compressed bytes; discard an original only after verifying that compressed bytes were stored successfully. Do not remove an original which is already referenced by an active review: existing assets need a separate guarded migration policy, and user choice does not resolve that race.
5. For avatars, coordinate PUT, DELETE and account-deletion cleanup per owner. With current fixed key, a delayed job cannot safely identify an obsolete generation; use durable cross-instance serialization/revalidation, or change to versioned immutable keys plus an authoritative current pointer and CAS-style replacement. The in-process photo decode slot is not such serialization (DELETE does not take it and other isolates exist).
6. Compression seam: website validator -> bounded resize/encode -> output validation -> existing store; mobile camera/picker -> equivalent normalization -> exact upload. Current validator returns original bytes and is not a compressor. Workers Free is confirmed target, but no CPU/peak-memory/codec acceptance is established; do not claim the current full decoder or added compressor fits 10 ms. Choose processing placement only after measuring or an explicitly budget-compatible design. Gate stays closed until real resource/runtime acceptance.

Verification to require when implementation is authorized: partial-majority and resubmission retention; dispute/financial hold exclusion; restored task/new-hold vs cleanup concurrency; exact-key deletion retry after timeout; failed upload/failed submit orphan handling; stale avatar delete vs newer PUT/account deletion; portrait/landscape aspect ratio and no upscale/crop unless chosen; tiny/large/corrupt images and final MIME/bytes; actual Free Worker CPU/memory.
