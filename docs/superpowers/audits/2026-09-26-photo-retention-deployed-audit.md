## Confirmed current bypasses

1. **An owner can delete active verification images.** `storage.objects` has both `Task owner can delete inactive verification images` using `ante_private.can_delete_verification_object(name)` and the older `Task owner can delete verification images`, whose entire condition is bucket `Verification Images` plus task ID from the first path segment owned by `auth.uid()`. The latter has no submission, terminal, retention-age, financial, or dispute condition; the extra restrictive policy cannot narrow an independent permissive allowance. Thus changing only the helper is insufficient.
2. **The inactive helper itself conflicts with retention.** `ante_private.can_delete_verification_object(text)` (definition MD5 `4c9e318a41d3601e5c1761a44d8b8e9b`) allows owner deletion whenever task completed, failed, archived (`deleted_at` nonnull), OR proof-submitted timestamp null. It does not require seven days after final resolution. First rejection clearing the projection opens this helper while resubmission remains possible.
3. **Owners can directly rewrite retention inputs.** All three tables `tasks`, `task verification information`, and `tasks to verify` have effective INSERT/UPDATE/DELETE table grants to `anon`, `authenticated`, and `service_role`; RLS is enabled, not forced. This is not anonymous row access: applicable owner/verifier policies still matter. Tasks permit owner UPDATE and DELETE. Proof information permits owner INSERT and UPDATE including the proof projection; no DELETE policy was returned for that table. Review requests permit sender DELETE/INSERT and pending verifier UPDATE. No authority guard trigger is installed on these tables. Any authoritative retention ledger must not trust client-writable completion/archive/projection fields.
4. **Global task purge is active every 30 seconds.** Cron job 4 is named `purge-deleted-tasks-hourly` but has schedule `30 seconds`, active true, and exact command `SELECT public.delete_old_deleted_tasks()`. Its SECURITY DEFINER function is solely `DELETE FROM public.tasks WHERE deleted_at IS NOT NULL AND deleted_at < now() - interval '7 days'`; definition MD5 `b68a0c069b8f421144ba759e23ba8e72`. Both anon and authenticated have effective EXECUTE. There is no auth check or pending-review, resubmission, financial, dispute, or final-resolution criterion.
5. **Task deletion cascades away proof and financial metadata.** FKs from `task verification information`, `tasks to verify`, `payment_holds`, and `notifications` all reference tasks with ON DELETE CASCADE. The public owner DELETE path and scheduled purge can erase the references needed for retention/cleanup or financial evidence. No user task counts or affected records were queried.

## Other deployed evidence

- User-defined triggers on the three tables are only task `updated_at`, proof-verifier synchronization, and review-status notification. No task DELETE trigger protects evidence or removes Storage objects. The synchronization trigger deletes pending review requests omitted from the mutable verifier roster.
- `can_read_verification_object` MD5 `f56d7fec5c7ac23621860ebac33cd988` permits owner reads; verifier reads depend on an active task, current nonnull proof, current attempt, and pending review. Clearing projections loses verifier access, independently of whether bytes persist.
- `can_write_unsubmitted_verification_object` MD5 `1a7f4807d08f4e39e0e1867b24b2f1b1` allows active owner writes with null submitted timestamp and a valid first-attempt or resubmission window. Existing UPDATE policy permits replacing an old key during a later unsubmitted/resubmission window; immutable normalized evidence keys are not enforced.
- `Verification Images` is private, maximum 10,485,760 bytes; allowed MIME types JPEG, PNG, HEIC, HEIF, WebP. No dimension/normalization condition is enforced by this configuration. `profile-photos` is private, maximum 2,097,152 bytes, JPEG/PNG. Its sole returned policy is authenticated SELECT requiring `storage.allow_only_operation('object.get_authenticated')` and `profile_photo_private.can_read_photo(name)`; no client INSERT/UPDATE/DELETE policy was returned.
- Cron inventory: jobs 1 and 2 named payment captures; job 4 task purge; job 7 website callback limiter cleanup. No inspected cron command calls the `purge-deleted-tasks` Edge endpoint. Commands were not exposed wholesale: only boolean classification/hash and the literal-redacted job-4 command were read. Job 7 schedule is `* * * * *`; do not confuse its row-retention horizon with its schedule.
- Narrow source-pattern metadata search across public/ante_private functions found `delete_old_deleted_tasks` as the only function directly matching DELETE FROM tasks, and no direct DELETE FROM storage.objects. This is not a comprehensive dynamic SQL audit.

## Minimum implementation blockers

- Remove both direct-image deletion allowances and harden task/proof lifecycle mutation authority in a compatible migration, with negative tests. Restrict global purge EXECUTE and replace/pause its destructive eligibility before claiming retention is protected. Avoid unreviewed production mutation in this audit.
- An immutable asset/attempt ledger and protected authoritative final-resolution time/hold state are needed before new automatic deletion. Prevent hard task deletion from destroying protected evidence or payment metadata. Exclude all financial and unknown legacy evidence until its policy is approved.
- Existing seven-day archive purge is not seven-day final-resolution retention. Scheduler changes alone do not close owner DELETE/UPDATE or cascade paths.
- New cleanup must delete exact immutable keys via Storage API, retain retry/tombstone metadata, and coordinate eligibility with lifecycle changes. Profiles need generation-aware replacement/deletion so delayed cleanup cannot delete a new active avatar.
