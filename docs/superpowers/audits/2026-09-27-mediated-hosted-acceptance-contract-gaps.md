## 1. Fresh authorization evidence and controlled races

An image response, private headers, CF cache status, timing, aggregate provider call counts or a successful direct resolver probe cannot prove that this particular website request performed its final Auth and resolver. Random request bursts do not establish which committed change preceded the resolver's statement snapshot. No test may report those stronger gates as passed from such evidence.

Smallest safe split:

1. Build a black-box runner for real cookie requests, direct denial, warmed-cache isolation and changes committed **between completed requests**. Its receipt names these gates and keeps `fresh_phase_trace`, `controlled_midflight_races` and `hosted_resource_limits` explicitly unaccepted. This runner remains useful without production instrumentation.
2. Separately design passive production-safe observations if existing authorized Worker/provider logs can neither correlate both Auth calls nor distinguish the two resolver calls. A proposed record contains an internally generated invocation ID, phase ordinal, fixed phase label, result class, elapsed time and a run-scoped nonreversible selection correlation. Record completions after actual operations, not just intentions. No JWT, cookie, identity, Storage key/URL, service credential or provider body goes into logs or a public diagnostic endpoint. Missing, truncated, sampled or ambiguous records mean unverified. Correlation must link the exact browser response to the invocation; a client-supplied trace header is not authority. The observation mechanism and retention/access policy require independent review before source edits.
3. Controlled hosted barriers require their own reviewed artifact on an already-authorized isolated Worker/domain in the intended account/runtime. A candidate build-time-only observer can delay after real initial selection, while consuming the real Storage body, at the decode completion boundary and after real final Auth. It may only observe/delay/cancel; it must never replace a provider result, token, principal, resolver result, byte body or decode result. External control must be inaccessible to the production build and bound to one fixture run/request, with bounded waits under the unchanged 30-second route deadline. No public header/query/secret flag may enable it in the normal endpoint. This is a design candidate, not an approved implementation contract.

The race artifact would preserve actual Auth, SQL resolver, manifest and Storage traffic and commit only owned SQL transitions before release. It proves that artifact's reaction to real changes; separate uninstrumented exact-URL replays on the intended route remain necessary. A barrier after decode cannot honestly claim a mutation occurred *during synchronous WASM execution*. Decide whether the accepted requirement is the validation-to-final-authorization boundary, or whether real concurrent validation evidence is still required. No replacement validator or auth bypass is acceptable.

A smaller race alternative is a fixed-purpose operator-only hosted probe importing the same production handler/modules. Within one invocation, a request-scoped transport/codec wrapper can await a real owned Supabase transition at the selected barrier, then resume unchanged provider/decoder results. This avoids assuming two requests reach one in-memory coordinator. It requires a separately reviewed way to supply invocation-local wrappers and the genuine OpenNext/Cloudflare environment; today's hard-wired module imports do not supply that interface. Never monkey-patch global fetch/decoder state across requests. The probe may establish hosted pipeline/race evidence, not trusted public ingress, browser or CDN behavior. Pair it with the uninstrumented external acceptance and keep artifact/source equivalence explicit.

For each race, evidence must distinguish initial-selection completion, committed transition acknowledgment, final resolver dispatch/completion and response emission. A transition committed before final dispatch is sufficient for the required snapshot ordering; wall-clock timestamps from unrelated machines alone are not. Include replacement, clear, friendship revocation, caller profile removal and target profile removal; separately classify real Auth logout/deletion effects without claiming stronger provider JWT revocation semantics. Changes after final authorization retain the documented in-flight limitation.

## 2. Admission isolation and all 22 fingerprints

`callback-admission.ts` derives visitor admission from `HMAC(secret, 'website-account:v1:' + trusted Cloudflare IP)` and user reads from `HMAC(secret, 'website-photo-read:v1:' + userId)`. Both use the real fixed 60-per-minute RPC. Synthetic user IDs isolate user digests, but do not isolate a shared visitor IP/digest. An injected `cf-connecting-ip` or a run-ID header is not a solution: direct Cloudflare ingress must supply the identity.

Recommended candidate: an already-authorized isolated acceptance Worker uses its own run-specific `ANTE_AUTH_LIMIT_HMAC_SECRET`, supplied through separately reviewed deployment configuration. Keep the public Pages deployment and its HMAC untouched. Keep both domain strings, real Cloudflare IP processing and quota RPCs unchanged. One closed-to-other-traffic Worker/run and a fresh secret can isolate visitor/user digests without changing production admission behavior. Do not expose the secret to the runner receipt or add a production run-namespace override.

Concrete missing input: how the runner obtains and pre-journals the exact visitor digest before the first HTTP request mutates admission rows. The release controller must either provide a reviewed manifest derived from the pinned secret and canonical ingress IP, or approve a private read-only preparation mechanism. IP uncertainty/change, multiple unaccounted browser egress addresses, reused secret, pre-existing digest rows or other traffic blocks the attempt. A diagnostic admission request cannot discover the digest before its own side effect. A preparation mechanism must not trust a spoofable IP header.

Persist the digest allowlist, zero-row precondition and every maximum admission reservation before website dispatch. Track exact observed row IDs where available. Reconciliation may delete only matching run-owned rows whose digest, interval and exclusivity are established; neither broad timestamp cleanup nor deleting all account-limit rows is allowed. Preserve the original 22-table baseline/final comparison, including `website_callback_private.admissions`; do not omit that table or silently redefine its digest.

There is a second independent hazard: the existing once-per-minute cleanup function expires rows across the entire admissions table. Even isolated run digests do not prevent unrelated baseline rows from disappearing during a run. Strongest unchanged-contract option: begin with an empty admissions table and establish operational quiescence for all other admission writers during the bounded acceptance window. Do not disable the scheduler or delete unrelated rows to make that true. If unavailable, report preservation drift/incomplete acceptance, or seek a separate explicit decision on an expiry-aware preservation contract. A test run cannot invent that exception.

## 3. Real cookies, refresh and request budgets

Use the installed `@supabase/ssr` 0.8.0 and `@supabase/supabase-js` 2.106.0 for real synthetic Auth sessions and cookie serialization. Use separate owner/friend/stranger cookie jars; anonymous has none. Send requests through the actual trusted Cloudflare domain, not Worker service binding ingress, with the same exact `/api/profiles/<owner>/photo` URL, no cache-busting parameter and no optional client cache-bypass headers. Verify Set-Cookie application, path/Secure/SameSite behavior and subsequent reads in a real browser before claiming browser acceptance; a Node cookie jar establishes only HTTP-cookie acceptance.

A cookie containing arbitrary synthetic JWT text is not a real-session test. For bounded initial-refresh acceptance, a candidate is a genuine current access/refresh pair serialized with expired client session metadata so the installed SSR SDK actually invokes refresh; leave JWT claims/signature unchanged. Fresh `getUser` and resolver still decide all authority. Label this induced SSR-refresh compatibility, not natural JWT expiry. Confirm this deterministic procedure locally with the installed SDK before approving it. Do not shorten global JWT lifetime, wait for expiry, add a test login route or bypass final checks. The exact bootstrap/refresh network calls belong in the ledger.

Per-request provider envelope for a fully successful read with an existing valid cookie:

| Dispatch | Auth | Data | Storage | Website |
| --- | ---: | ---: | ---: | ---: |
| Ordinary successful read | 2 | 5 | 1 | 1 |
| Initial refresh variant, assuming one verified refresh dispatch | 3 | 5 | 1 | 1 |

The five Data calls are visitor admission, user admission, initial resolver, service manifest and final resolver. A caller denied by initial resolver still consumes two admissions, one Auth call and one resolver. An absent cookie normally consumes visitor admission without Auth/provider photo work. Reserve a complete allowed envelope **durably before each website dispatch**, because the runner cannot fsync before internal Worker subrequests. Reconcile reservation with correlated traces when available; do not present estimated subrequest counts as observed counts. Never release unused budget to retry a timed-out request that may still execute.

A final numeric run budget cannot be inherited from the old 170-call ceiling: it depends on the selected route matrix, refresh bootstrap, number of race cases/generations, browser ancillary requests, observation/control transport and recovery SQL. Before implementation approval, enumerate every scenario and operation in a machine-readable ledger; calculate separate direct Auth/Data/Storage/CLI, website envelopes, observer/control and cleanup counters, total ceilings and wall-time cap. Assert the full worst-case first cleanup and every explicit recovery epoch fit their independent reserves. Keep normal intended website reads below 60 per visitor/user rolling minute unless a separately budgeted quota test is intended. No quota reset or wait-to-pass strategy.

## 4. Cutover, direct denial and fresh fixture ownership

Separate three contracts: read-only predecessor release preflight; an independently reviewed operator SQL/config/cache cutover receipt; and post-cutover runner preflight. Fresh catalog pins differ across cutover. Do not let a runner assume, install, repair or roll back policy/manifest/mode/cache rules. The runner requires all 14 named mediated postconditions exactly once and true, empty objects/heads/operations/multipart inventory, no in-progress producer and all 22 fingerprints. The Worker/domain/cache-rule/build identities must be pinned separately from the SQL catalog.

Before any object creation, use real ordinary sessions plus anonymous probes against predetermined absent paths and the exact catalog/RLS denial checks. An absent-key 404 alone proves no object retrieval, not the authorization policy; report that distinction. Do not upload a canary merely to make this preliminary check stronger. Fresh asset UUID/key comes from the service reserve RPC, whose operation intent is journaled first; persist its reconciled authoritative result before upload. Do not claim the asset UUID itself can be preselected locally. No legacy `avatar` fixture or previously exposed object key.

After first object creation, perform a real privileged read of each exact immutable fixture URL, then owner/friend/stranger/anonymous ordinary requests to each applicable direct object/authenticated/public/render/sign/list route. Freeze the exact endpoint/method/header/body matrix from supported deployed routes during design review; old owner-only descriptors are not complete. Any returned image bytes, successful signed URL or unauthorized object listing fails isolation. Provider-unsupported rendering is separately reported, not inferred as authorization success. A warmed direct leak fails this transport candidate; no retries with random URLs, header changes or expiry delays.

Black-box website cases can then prove owner/friend current-byte digests, stranger/anon denials, prepared-generation invisibility, publication of a different digest, revoke/regrant, clear and exact saved URL replay. Repeat success URLs using same/different cookies and Range/If-None-Match/If-Modified-Since; require full fresh 200 or explicit denial, never 206/304. Assert every response has the accepted browser/CDN no-store headers and prohibited validators absent. Keep profile-deletion transitions and phase races distinct if the bounded first runner does not include them; an incomplete matrix cannot earn overall acceptance.

Cleanup must reconcile each pre-journaled operation and lost acknowledgment, never repeat create/upload/publish/clear. Lost upload with an absent key remains unresolved because delayed completion is possible. Delete only exact owned metadata/objects/users after marker, email, created-at, revision, manifest, multipart and full protected-reference checks. Check owned admission reconciliation before final fingerprints. Distinguish failed assertions, blocked cleanup, recovered cleanup and preservation drift; retain journals outside Git and receipts without credentials/cookies/identifying provider bodies.

## Smallest next source package and four decisions

The controller can choose a **partial black-box package** now, after fixing its finite scenario/endpoint ledger and admission preparation contract. Proposed files are `scripts/acceptance/hosted-profile-photo-mediated.mjs` (state, journal, descriptors, bounded scenario orchestration), `hosted-profile-photo-mediated-port.mjs` (fixed provider/website transport), `hosted-profile-photo-mediated-sql.mjs` (ownership/admission inventory and guarded cleanup), their three `*.test.mjs` files, and a new operator audit. `package.json` gains only the corresponding local test entries. Preserve the accepted production reader source and both historical runners. A separate cookie helper/browser test file should be added only once HTTP-cookie versus real-browser scope is chosen.

Its local TDD gates must cover import-without-provider-access, pre-dispatch fsync and envelope exhaustion, crash/late-response recovery, forged journal ownership, partial identity/asset creation, no legacy/reused key, all 14 postconditions, every ledger branch, no automatic deployment, leaked warm response failing closed, exact owned admission teardown and complete 22-table preservation. Disposable PostgreSQL tests must prove unrelated fixture/admission/Storage rows block or survive cleanup. Provider fakes test runner mechanics only. No hosted claim follows from these passing tests.

Four decisions are necessary before converting this audit into an executable task plan:

1. Is the next deliverable explicitly partial black-box HTTP acceptance, with controlled hosted phase races, passive tracing, real-browser behavior and resource measurements separately open, or must any of those be included in this package?
2. Can the intended isolated Worker use a dedicated run HMAC and exclusive traffic, and what reviewed preparation mechanism supplies its canonical-IP digest before the first admission side effect? Can unrelated admission-table writers be quiesced with an empty baseline?
3. For the stronger race package, is a separately built, privately controlled, delay-only observation artifact acceptable, and does the validation-to-final-check boundary satisfy the stated decode-race requirement? If not, retain the gate as blocked rather than weaken the ordinary endpoint.
4. Which fixed direct-route/scenario matrix and deterministic real-session refresh bootstrap are approved, so exact run, subrequest, browser and cleanup ceilings can be computed and tested without silent retries?

No temporary Cloudflare account, preview URL, paid-resource workaround, public auth override, production HMAC rotation or mode activation is proposed. The existing account and intended isolated Worker/domain need authorized access before a hosted attempt. The controller owns the main goal handoff update and approval/review coordination.
