# Private photo endpoints implementation plan

> For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development and test-driven-development.

**Goal:** Implement the selected account photo PUT/DELETE and owner/current-friend GET backend contracts, closed by default until resource and hosted acceptance is complete.
**Architecture:** Reuse durable admission and isolated public-key SSR cookies; verify the exact caller token with Auth before using it. A small server-only adapter performs fixed-path provider requests, with privileged credentials limited to photo mutations. The accepted validator handles original image bytes. No new SQL is needed.
**Tech Stack:** Existing Next 16.3.3/OpenNext 1.20.6, Supabase SDK 2.106.0, pinned jSquash validator; paired Storage API 1.74.0 isolated fixture.
**Spec:** docs/superpowers/audits/2026-09-25-private-avatar-contract.md; docs/superpowers/audits/2026-09-26-private-photo-endpoint-preparation.md; docs/superpowers/audits/2026-09-26-profile-photo-validator-local-acceptance.md.

Existing website worktree only, except Task 1's exact paired backend HTTP test and release receipt. No UI/mobile, schema migrations, provider mutations, real credentials/photos, deployment, paid services, financial code or retained-fixture access. No subagents by implementers. Caller token only for profile-existence checks and photo reads; service credential only for the existing limiter and fixed-key PUT/DELETE provider operations. Never log provider bodies, tokens, IDs, paths, image bytes or decoder warnings. No automatic mutation retry.

Operator gate `ANTE_PROFILE_PHOTOS_MODE=private-v1` is server-only and unset by default. Do not configure it in production or example deployment vars. Closed routes return private503 before admission/Auth/Storage/decode. Hosted Auth/JWKS, opaque-key Storage gateway behavior, revocation/cache/transform nonexposure, cookie/browser ingress, whole-validation-pipeline CPU/peak isolate memory and target Workers plan remain release gates. Implementing a gated route does not satisfy those gates.

Read body/decode only after visitor admission, fresh exact-token Auth verification and per-user action quota. Reuse current 60/min visitor RPC; new user namespaces use existing fixed 5/min callback RPC separately for upload/delete and 60/min account RPC for read. HMAC verified caller IDs with distinct `website-photo-upload:v1:`, `website-photo-delete:v1:`, `website-photo-read:v1:` prefixes. No new tables or mutable runtime quota configuration. Denial429 and unavailable503 have safe Retry-After; all responses private/no-store.

## Review Focus

Caller-controlled cookies, target IDs and headers must not select privileged storage locations or substitute identity. Task 2 tests a forged cookie user alongside a different fresh Auth user/token.
Provider successes with malformed or wrong-key bodies must not become mutation success; transport uncertainty must not replay. Task 1 tests exact response mapping and no retries.
Slow, oversized or never-ending provider bodies must not evade the deadline/cap or leak raw details. Task 1 tests bounded response reads, abort and cancellation.
A rejected upload must not be read/decoded before admission, and verified refresh cookies must survive downstream denials. Task 2 tests ordering and all post-verification result classes.
Cache validators, unsupported methods and public-mode configuration must not bypass fresh authorization. Task 2 tests 405, closed gate, conditional/range requests and private response headers.
