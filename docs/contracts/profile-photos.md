# Private profile photo backend contract

The fixed Storage adapter described first remains server-only and does not authorize callers or validate downloaded images. The gated website endpoints below supply admission, fresh Auth verification, full image validation and private responses. The release remains closed until hosted gateway, CDN/JWKS, cookie and resource checks pass.

`lib/server/profile-photo-store.ts` derives the only object key as `<canonical lowercase UUID>/avatar` in the private `profile-photos` bucket. A caller cannot provide a bucket, key, origin, URL or extra headers. It uses the project origin and public key from `accountConfig()`. Its owner-existence query is `GET /rest/v1/profiles?select=id&id=eq.<owner>&limit=2` with the public apikey and the verified caller bearer token; only one exact `{id}` row counts as existing. Hosted metadata checked 26 September shows authenticated `profiles.id` SELECT with an own-row `auth.uid() = id` policy, but no real-token REST receipt was taken. Profile existence is a precondition, not an account-deletion race guarantee.

| Operation | Exact provider request | Accepted reply |
| --- | --- | --- |
| Upload | `POST /storage/v1/object/profile-photos/<id>/avatar` with `x-upsert: true`, `cache-control: max-age=0`, original JPEG/PNG bytes and matching Content-Type | Any 2xx JSON object with `Key` exactly `profile-photos/<id>/avatar`; optional `Id` must be a nonempty string. |
| Delete | Single-object `DELETE /storage/v1/object/profile-photos/<id>/avatar` | HTTP 200 JSON message `Successfully deleted`, or HTTP 400 with string `statusCode: "404"`, `code: "NoSuchKey"`, `error: "not_found"`. Error message text is never trusted for classification. |
| Download | `GET /storage/v1/object/authenticated/profile-photos/<id>/avatar` with public apikey and exact verified caller bearer | HTTP 200 original JPEG/PNG bytes up to 2 MiB; HTTP 400 with string logical status 404 and `NoSuchKey`/`NoSuchBucket`, or logical status 403 and `AccessDenied`, maps to `not_found`. Other errors map to unavailable. Stored bytes are raw and still require full image validation by the endpoint. |

Only fixed-key upload/delete use `serviceCredential()`. Opaque `sb_secret_` keys are sent as apikey alone; a legacy service-role JWT is sent as apikey and bearer. An invalid configured opaque key does not fall back to the legacy variable. Reads and profile checks never look up the service key. All requests reject redirects, avoid cache and retry, use one ten-second deadline across transport and body consumption, cap JSON bodies at 16 KiB and photo bodies at 2 MiB, and cancel rejected streams without awaiting an untrusted producer. Protocol, timeout and transport uncertainty return fixed unavailable results without raw logs. A 503 after a mutation does not prove Storage stayed unchanged, and concurrent operations can supersede each other.

The [26 September source and OpenAPI research](../superpowers/audits/2026-09-26-private-photo-storage-protocol.md) compares pinned Storage API 1.74.0 [single-object DELETE source](https://github.com/supabase/storage/blob/01c95148a981a88b5f7e9014571a2926567b51e3/src/http/routes/object/deleteObject.ts) and [published OpenAPI](https://supabase.github.io/storage/api.json) against installed Storage JS 2.106.0 bulk remove. The SDK `remove([path])` uses the bulk endpoint, whose empty success does not establish single-key deletion. This adapter uses the documented single-object endpoint. The paired isolated Storage HTTP test confirmed initial/upsert HTTP 200 with exact `Key` and nonempty `Id`, single DELETE HTTP 200 exact message, second DELETE HTTP 400 with `NoSuchKey` and string logical 404. Its read denials confirmed `NoSuchKey` and `NoSuchBucket` logical 404; the common error handler's `AccessDenied` logical 403 was observed on rejected mutations. Hosted Storage/gateway acceptance remains open; the local synthetic-JWT fixture does not establish opaque-key gateway behavior.

## Gated website endpoints (26 September 2026)

The website now implements `PUT` and `DELETE /api/account/profile/photo` plus `GET /api/profiles/<ownerId>/photo`. They are server-only, dynamic Node routes and remain closed unless `ANTE_PROFILE_PHOTOS_MODE=private-v1` is set on the server. That value is absent from deployment configuration. The route returns a private 503 while closed; this implementation does not activate photo serving.

| Request | Input and success | Fixed denials |
| --- | --- | --- |
| PUT `/api/account/profile/photo` | Same canonical Origin/Host; no query; raw JPEG or PNG body up to 2 MiB. The existing validator checks complete structure and decodes it. A confirmed fixed-key Storage upsert returns `200 {"ok":true}`. | 400 malformed input, 403 origin, 408 body deadline, 413 size, 415 MIME, 422 invalid image, 401 Auth, 404 missing own profile, 429 quota, 503 closed gate/provider/decoder or uncertain write. |
| DELETE `/api/account/profile/photo` | Same canonical Origin/Host; no query or body. A confirmed delete or exact Storage already-missing receipt returns `200 {"ok":true}`. | 400 input, 403 origin, 401 Auth, 404 missing own profile, 429 quota, 503 closed gate/provider or uncertain write. |
| GET `/api/profiles/<ownerId>/photo` | Canonical lowercase UUID target and no query. A fresh caller-JWT Storage read is fully validated and returns original bytes, JPEG/PNG Content-Type, `X-Content-Type-Options: nosniff`, and private/no-store. | 400 target/query, 403 origin, 401 Auth, 404 Storage missing/denied, 429 quota, 503 closed gate/provider/stored corruption. |

Unsupported methods, including HEAD and OPTIONS, return bodyless private 405 with exact `Allow: PUT, DELETE` or `Allow: GET` before Auth. Rejected PUT bodies are cancelled without waiting on their producer. Every response is private/no-store; 429/503 includes safe `Retry-After` guidance. No provider body, token, URL, signed URL or encoded image enters JSON. GET ignores client range and conditional headers, always verifies the caller and fetches a complete private object, and never returns 206/304 or forwards provider validators/cache headers.

Valid requests consume the existing 60/min direct-Cloudflare visitor admission before SSR/Auth or body reading. The isolated SSR stage uses `getSession()` only for its access token, then calls `getUser(thatExactToken)` for a fresh canonical UUID. The unverified `session.user` and cookie claims are never authority. The same checked token goes to the public-key profile existence query and caller-JWT Storage download. The verified user ID selects the only fixed mutation key. Failed verification discards provisional refresh cookies; all later success and denial responses retain them. Separate HMAC namespaces `website-photo-upload:v1:`, `website-photo-delete:v1:` and `website-photo-read:v1:` consume the existing fixed callback RPC at 5/min for each write action and the account RPC at 60/min for reads. An own-profile check precedes privileged PUT/DELETE, and image body reading/decode follows both admissions. These are request-level controls; concurrent account deletion still needs a cleanup contract.

The [local route acceptance audit](../superpowers/audits/2026-09-26-private-photo-route-local-acceptance.md) records actual-SDK cookie/refresh/Auth and real-codec PNG PUT/GET tests, full website checks and Worker build. Local doubles and a synthetic Worker build do not establish hosted opaque-key gateway behavior, real JWT/RLS/friendship decisions, browser cookies, cache/transform nonexposure, or full-image CPU and peak isolate memory on the target Workers plan. Keep the mode unset until those checks and the account-deletion cleanup decision are resolved.
