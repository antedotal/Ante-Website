# Private profile photo reader contract

The website's only active photo path is `GET /api/profiles/<ownerId>/photo` when the server-only `ANTE_PROFILE_PHOTOS_MODE=generation-read-v1` gate is explicitly set. The gate is unset in deployment configuration, so this source change does not activate hosted photo serving. `private-v1` is retired: it enables neither reads nor fixed-key writes. `PUT` and `DELETE /api/account/profile/photo` always return the existing private 503 after cheap request validation; rejected upload bodies are cancelled without waiting for their producers. The low-level fixed-key upload, delete and owner-profile helpers remain in `lib/server/profile-photo-store.ts` as dormant code pending the compression and generation write protocol. They are not called by these routes.

For a read, the route validates the canonical lowercase owner UUID and query, admits the visitor, verifies the exact caller token with fresh Auth, admits the verified user at 60/min, and acquires the shared per-module photo-processing slot. It then calls `POST /rest/v1/rpc/resolve_profile_photo_v1` with `{ "p_owner": "<owner UUID>" }`, the public apikey and that same verified bearer token. Only an HTTP 200 JSON object with exactly one of these shapes is accepted:

| Resolver reply | Derived private Storage key |
| --- | --- |
| `{ "kind": "legacy" }` | `<owner UUID>/avatar` |
| `{ "kind": "current", "asset_id": "<canonical lowercase UUID>" }` | `<owner UUID>/<asset UUID>` |
| `{ "kind": "not_found" }` | No Storage request; route returns 404. |

Malformed, extra-field, non-JSON, redirected, oversized or uncertain replies return a fixed 503 with no Storage request. Resolver responses expose no manifest, hash, lease, operation ID, object key or bigint revision. Backend authority checks the live caller and target profiles, owner equality or accepted friendship in either direction, and the exact current head and completed upload operation. Legacy is available only before any committed revision. A revision-zero reservation preserves an existing legacy photo; a clear or replacement cannot restore it. The corresponding private Storage SELECT predicate makes the final authorization decision for the derived key, including when friendship or the head changes between resolution and GET. Already in-flight bytes cannot be retracted after revocation, and the two network calls are not atomic.

The website sends one `GET /storage/v1/object/authenticated/profile-photos/<derived key>` with the public apikey and the same checked bearer token. It does not forward browser cookies, Range or conditional headers, use a service credential, retry, re-resolve, or fall back to legacy after a denial. The existing provider helper gives each resolver and Storage call its own ten-second deadline across fetch and body reading, rejects redirects, cancels rejected bodies, limits JSON to 16 KiB and photo bytes to 2 MiB. Exact pinned Storage missing/access-denied replies map to 404; ambiguity maps to 503. The route fully validates and decodes returned JPEG/PNG bytes, then returns the validated complete image with `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. It never returns partial or conditional responses or provider validators. Publication already attests the immutable manifest; this read path does not independently verify manifest integrity.

All denials use fixed private JSON errors. Failed Auth discards provisional refresh cookies; every later outcome retains them. Visitor admission precedes SSR/Auth, and user admission precedes resolver/Storage. The one synchronous processing slot covers resolution, Storage download, validation and response construction. Contention returns private 503 with `Retry-After: 60`. It is per loaded module/isolate and does not bound retained response bytes or work in other isolates.

The dormant low-level fixed-key helpers still use their prior exact Storage receipts. Only those mutation helpers call `serviceCredential()`; opaque `sb_secret_` keys are sent as apikey alone and legacy service JWTs as both apikey and bearer. The existing admission transport separately uses its privileged quota credential. Resolver and download use only the public key and caller JWT. Earlier adapter protocol evidence is in the [Storage audit](../superpowers/audits/2026-09-26-private-photo-storage-protocol.md); earlier route evidence is in the [route audit](../superpowers/audits/2026-09-26-private-photo-route-local-acceptance.md).

This reader slice is source and disposable-backend verified only. Hosted rollout still needs coordinated SQL policy activation and real-token/private Storage acceptance. The accepted [compression and retention requirement](../superpowers/audits/2026-09-26-photo-compression-retention-requirements.md), generation writes and safe cleanup remain separate work. No hosted gate or provider configuration was changed here.
