# Website email one-time-code contract

`POST /auth/email/request` accepts exactly `{ "email": string }`. `POST /auth/email/verify` accepts exactly `{ "email": string, "code": string }`. Both are Node-runtime, server-side Next.js routes. The code is 6–10 ASCII digits as a string, so leading zeroes survive. Email is trimmed and lowercased, capped at 254 characters and checked as an ordinary address. No request may set a redirect destination or provider options. Other HTTP methods are not implemented.

Both routes require the configured canonical HTTPS site origin (HTTP is allowed only on localhost), a matching `Origin`, URL origin and `Host`, and consistent forwarded host/protocol when present. Missing, `null`, hostile or inconsistent origins fail before body parsing or network work. The handler then consumes the existing Cloudflare visitor-IP admission. It reads no more than 4096 streamed bytes of `application/json`, decodes UTF-8 strictly, requires a plain object and rejects extra keys. A valid normalized email consumes a second HMAC-SHA256 bucket under `website-auth-email:v1:`. Both actions share that email bucket, even if a visitor changes IP. The raw email is never sent to the limiter. Both buckets call the historical `consume_website_callback_limit` RPC at its fixed five admissions per rolling minute; the website cannot choose the quota or time. The RPC adapter's privileged key is used only for admission. Supabase Auth uses the public SSR client.

Request calls `signInWithOtp` with `shouldCreateUser: true`, so this path allows new and existing accounts. Accepted requests and ordinary provider account rejections both return `202 {"ok":true}`. They return no session cookies, user details or tokens. Verify calls `verifyOtp` with type `email` and returns `200 {"ok":true}` only when the provider returns both a user identity and a session; the session is carried by SSR cookies, not JSON. Failed and provisional verification responses carry no session cookies. Auth cookies use `Path=/`, `SameSite=Lax`, no widened domain and `Secure` for HTTPS; HTTP localhost remains usable. Browser-readable cookies remain necessary for the current browser SDK architecture.

Errors carry fixed messages and `Cache-Control: private, no-store`: 400 malformed input, 401 invalid/expired verification, 403 untrusted origin, 413 oversized body, 415 unsupported content type, 429 visitor/subject/provider throttle and 503 unavailable configuration, store or provider. A 429 includes `Retry-After` from the admission RPC or 60 seconds for a provider throttle; 503 includes `Retry-After: 60`. Logs contain fixed labels only.

The website admission buckets protect these routes, but public Supabase Auth remains directly callable. Provider-side rate limits, CAPTCHA, SMTP and template settings require separate acceptance. Supabase sends a magic link by default until its email template includes `{{ .Token }}`. Before linking this sign-in flow publicly, verify real email delivery for existing and new accounts, OTP length/expiry, same-account Google/email linking and Worker `Set-Cookie` behavior with an authorized test recipient. Local mocked tests establish the route contract, not those hosted settings or delivery. Cloudflare Pages remains the live site while the Worker is prepared.

Provider references: [passwordless email guide](https://supabase.com/docs/guides/auth/auth-email-passwordless), [signInWithOtp](https://supabase.com/docs/reference/javascript/auth-signinwithotp), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp).
