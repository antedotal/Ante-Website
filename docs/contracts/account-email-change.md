# Authenticated account email change

`POST /api/account/email-change/request` accepts exactly `{"newEmail":"new@example.test"}`. `POST /api/account/email-change/confirm` accepts exactly `{"email":"current-or-new@example.test","code":"001234"}`. Addresses use the existing sign-in normalization rule; codes are 6–10 ASCII digits kept as strings. Both routes require the configured canonical URL, Host, matching forwarded host/protocol, an exact same-origin `Origin`, no query string, and `application/json` of at most 4096 streamed bytes. Invalid input returns 400, oversized bodies 413, unsupported media 415, and hostile origin/host 403, before network work. Other methods, including HEAD and OPTIONS, return bodyless private 405 with `Allow: POST`.

The server-only `ANTE_EMAIL_CHANGE_MODE=secure-two-inbox-otp` setting must be explicitly present. Missing or any other value returns private 503 with `Retry-After: 60` before Auth. Keep it **unset** in deployment configuration until hosted email confirmations and Secure Email Change are independently verified as enabled, the Change email address template is verified to deliver distinct OTPs to the current and new inboxes, and authorized two-inbox acceptance passes. This setting is an operator gate, not proof of provider configuration. It is not a public `NEXT_PUBLIC_` variable. The routes additionally need the normal account public project/site values and the existing direct Cloudflare visitor and HMAC/service credential admission settings; there is no alternate local bypass.

After input and gate checks, each call consumes the fixed 60-per-minute account visitor admission before constructing a public-key SSR Auth client. `auth.getUser()` must establish a nonempty ID and valid current address; session cookies and user metadata are not identity evidence. A separate fixed five-per-minute callback-store bucket, HMAC keyed by that verified ID, applies to each action. The service credential is used only for those fixed admissions. Invalid/expired identity returns 401 without provisional refresh cookies; Auth throttling returns 429 and transport/unavailable failures return 503, each with `Retry-After: 60` where appropriate. Once identity succeeds, its legitimate refresh cookies may accompany later fixed failures.

The request route rejects an unchanged target and calls only public `auth.updateUser({email})`. A semantic provider 4xx rejection returns the same private `202 {"ok":true}` as a successful request, without mutation cookies. This reduces a duplicate-address response oracle; the caller's own pending state and public Auth can still be observed. Provider 401/403 means 401, 408 means 503, 429 means 429, and unknown/transport/5xx means 503. A provider success receives 202 only after fresh `getUser()` confirms the same ID, unchanged current email, and exact pending target. `202` means the request was received; it does not promise provider acceptance, delivery, or that the primary email changed.

Confirmation requires a fresh distinct current/pending `new_email` pair from `auth.getUser()`. The submitted address must equal one member before any OTP is consumed. The route calls only public `verifyOtp({email,token:code,type:'email_change'})` from an isolated cookie stage. Invalid, expired, or replayed codes return fixed 401; 429 and unavailable conditions remain distinct. An error-free result with both user and session null returns `200 {"status":"pending"}` only when another `getUser()` on the original verified stage still shows the same ID and unchanged pair. Pending means only that the account still has the change; it does not say which inbox code was accepted. A result with a session returns `200 {"status":"completed"}` only when returned user and session-user IDs match the caller, both emails equal the snapshotted target, both pending fields are absent/null/empty, and fresh `getUser()` on the child confirms the same completed state. A partial or inconsistent result, changed target, or postflight outage returns fixed 503. A consumed OTP cannot be rolled back; refreshing account state is the recovery step after uncertainty.

Only explicitly verified cookie stages reach responses. An initial refresh can survive a later failure; rejected mutation writes, removals and SDK-created PKCE verifier cookies are discarded. Accepted completion applies the child stage after the initial stage so its replacement/removal wins. All responses are private/no-store and omit addresses, codes and provider details. Local tests exercise routes and installed SDK behavior with synthetic transport. Hosted two-inbox OTP delivery, fresh pending-field exposure, browser and Worker cookies, shared-project identity, and direct Cloudflare ingress still require external acceptance. No real recipient was used in this implementation.
