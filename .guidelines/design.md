# Website runtime design

The website uses Next.js, React and the pinned pnpm/OpenNext Cloudflare toolchain. Package and lockfile versions are authoritative. Public build configuration is validated before compilation; private credentials are supplied outside tracked files.

## Closed payment publication boundary

This distribution includes the required card, consent, task funding, collection recovery, payment review/notices and Premium account surfaces. `paymentWebsiteSourceEnabled()` returns false for this distribution because private source-acceptance evidence is omitted. Environment presence cannot activate a financial flow. Its existing downstream gates remain in place. Canonical unavailable pages render before account/Auth or credential admission; Scoped review/collection aliases and unsafe requests retain their strict original fences; card/funding/Premium preserve their existing unavailable-page matching behavior. A separately reviewed source transition is required before financial activation.

The task UI binds affirmation to the displayed quote identifier/hash/task revision; the server compares that selection against its owned cookie before financial admission. The server remains authoritative for amount, currency and snapshots. Recovery retains original operation/owner identity, current billing revision/generation and pending locks. Provider-verified paid intervals and task commitments are independent of nonpaid status. Synthetic previews do not establish provider or entitlement acceptance.

Pricing, caps, approved terms and live financial configuration remain external prerequisites. No subscription or task charge is activated here. Existing public legal pages are preserved. The new runtime payload excludes private evidence, fixture DSL, source pins/witnesses and backend SQL installations. Unrelated already-published source, tests, documentation and assets remain inherited unchanged; they grant no runtime or financial acceptance. Behavior tests exercise the actual account components, HTTP/cookie selection and closed publication gates; local compilation or synthetic tests cannot establish hosted/provider/financial acceptance.

Consent panels display the existing human-readable terms version and format recorded accepted/revoked dates using the Australian account date style. Raw policy hashes remain in DTOs, identity matching, affirmation and authorization checks but are not rendered as customer-facing text. Semantic time elements retain the original timestamp. No financial gate, consent action, policy approval or provider behavior changes.

## 2026-10-09 Payment action announcements survive owned rereads

AccountPayments previously cleared its action status after execute/consume refresh: a failed execution set the unknown-outcome instruction, then a successful context/cards reread replaced it with an empty live-status string. A call-local refresh announcement now preserves the existing exact action message through successful rereads, or presents it alongside the independent availability warning. Original request/operation correlations, recovery slots, consent/quote guards and owner/generation fences are unchanged; snapshot availability does not establish execution success. Local component-hook recording tests reproduce the original failure for lost HTTP 503 acknowledgement, returned unknown and pending states, verify the same original execute IDs, and ensure a delayed recovery reread cannot carry an old owner's message into a new owner. These are component-only controls with local responses, not browser/provider or hosted financial acceptance. Production payment gates and settlement pause remain unchanged.

## Original-card continuation and selected provider runtime

Card, task and Premium server entry points select the same closed provider runtime. Explicit card-only requests use `allowed_payment_method_types: ['card']` without a conflicting payment-method configuration. Original failed-intent observations bind the original saved card, including the provider's nested error-card identity, before classifying decline or authentication-required outcomes. Authentication-required results retain the provider's `requires_payment_method` state; they do not imply payment or backing.

Original-card continuation requires a current, owner-bound, one-use ticket and an unchecked affirmation for the original task card. After affirmation, the client calls `confirmCardPayment` once with that original intent secret and saved method. Generation, expiry and attempt fences prevent stale or repeated activation. The ordinary seven-field authentication ticket retains its existing behavior. Confirmation then rereads canonical backing or payment progress; only those records establish state. Short-hold backing retains a polite, atomic live status after the transient authentication frame is removed, including the pending outcome.

Original full capture verifies the owned manual authorization and captures the exact remaining amount. The request omits the optional `final_capture` field, retaining its documented default of `true`; partial or multicapture behavior is not introduced. Provider results still require the exact original intent and charge, amount, currency, test mode and zero remaining capturable amount. Backend SQL installation changes are outside this website payload. Financial serving remains closed and settlement remains paused.

An ordinary issuer decline from the original create request may carry an unexpanded failed-charge ID. After verifying the original intent, owner, card, metadata and zero-money state, the same guarded transport may read that exact original intent once under its existing lease. The expanded failed charge must match the original pointer and complete identity and zero-money fields. Authentication, contradictions, expired leases and failed reads remain unknown; no create retry or new payment authority is granted.
